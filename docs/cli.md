# Command reference

`agentlab --help` and `agentlab <command> --help` are authoritative; this page
is the map. Every command runs against one lab — its `agentlab.yaml` (written
by `configure`; on a terminal, a missing file starts the form), `certs/` and
`state/` — and talks to its kind cluster through the cluster's own exported
kubeconfig, `state/kubeconfig`, never your shell's current-context.

## Where things live

agentlab keeps to the freedesktop folders, like every other program on the
machine (each `XDG_*` variable counts when it holds an absolute path):

| What | Where |
|---|---|
| The binary | `~/.local/bin/agentlab` (`$XDG_BIN_HOME`), where `self-update` installs it |
| A lab's configuration | `~/.config/agentlab/labs/<lab>/agentlab.yaml` (`$XDG_CONFIG_HOME`) |
| A lab's state: the lab CA and certificates (`certs/`), kubeconfigs and rendered manifests (`state/`) | `~/.local/state/agentlab/labs/<lab>/` (`$XDG_STATE_HOME`), the lab's directory; its `agentlab.yaml` links to the configuration |
| The registry of the labs | `~/.config/agentlab/labs.yaml` |
| The update check's cache | `~/.cache/agentlab/` (`$XDG_CACHE_HOME`) |

On macOS the configuration and the state are under `~/Library/Application
Support/agentlab/`, the cache under `~/Library/Caches/agentlab/`.

A lab is its name: it keeps its directory, and with it its CA, across `down`
and `up`. A lab from before these folders — a checkout, a directory of its
own — moves into them on the first command that enters it: its
`agentlab.yaml` to the configuration folder, `certs/`, `state/`,
`kubeconfig.oidc` and `.token` into its directory, each by a rename, nothing
copied or dropped, relative paths in `agentlab.yaml` made absolute first. The
command says so (`Moved lab agentlab from … to …`). Every moved file leaves a
link at its old path: the kind node of a running lab mounts `certs/` and
`state/node` by their old paths, and an older agentlab run in the old
directory still finds its lab. A lab on another file system than the state
folder stays where it is, said on stderr. A lab already in its directory
whose `agentlab.yaml` there is a file, not the link (the layout before the
configuration folder, or an older release's save over the link), has the
file moved to the configuration folder byte for byte on its first command,
the link in its place (`Moved lab agentlab's agentlab.yaml to …`); a copy
equal to the configuration folder's file gives way to the link, and one
that differs is refused, naming both files and the newer, until one of the
two is moved aside.

## Which lab

`configure` and `up` register their lab under its `clusterName`, so the
other commands find it from any directory, in this order:

1. `--lab <name>` (every command), refused naming the registered labs when no
   lab of that name is registered;
2. the `agentlab.yaml` in the current directory: the lab its `clusterName`
   names (a copy of a registered lab's file, or the link a moved lab left,
   enters that lab), else this directory's lab, which settles in the folders —
   always this directory for `render`, which writes the files of the
   `agentlab.yaml` it reads: a copy renders a scratch lab beside it and never
   rewrites the registered lab's `certs/` or `state/`;
3. a picker among the registered labs on a terminal, and off one a refusal
   that names them and `--lab`.

No lab is a default, not even the only one registered: a command runs against
the lab `--lab`, the directory or the person names, or refuses. An
`agentlab.yaml` without a `clusterName` is refused too: the file names its lab.

A lab entered from another directory is named on stderr (`Lab agentlab
(~/.local/state/agentlab/labs/agentlab)`). `configure` and `up` skip step 3:
in a directory without `agentlab.yaml` they create a new lab in the folders,
named `agentlab` — or the first free `agentlab-<n>` when another lab holds
that name — unless `configure --cluster-name <name>` names it. A
`clusterName` another lab holds is refused, naming both directories — the two
would collide on the kind cluster and its ports. `down` keeps the
registration (the lab still exists); a lab whose directory or
`agentlab.yaml` is gone is neither offered nor listed, and back once its
`agentlab.yaml` is (the next registration drops the entries still gone).
`agentlab list` also shows every kind cluster no registered lab names, marked
`lab directory unknown`: any command run in a lab's directory (`agentlab
pods`) registers the lab. `self-update`, `completion` and `help` touch no lab.

The commands that only read a lab — `trust`, `untrust`, `list`, `status`,
`open`, `pods`, `logs` — read an `agentlab.yaml` a newer agentlab wrote: a
field this release does not know is read past with a note naming the release
that wrote it, and nothing is written. Every command that writes the file
refuses it instead, so a newer release's switch is never dropped.

## Headless use

Nothing asks without a terminal (stdin not a TTY): no first-run question, no
lab picker, no trust or open offer. A missing `agentlab.yaml` is refused with
a pointer to `agentlab configure --defaults`, which writes the canonical lab
without a question; registered labs and no `agentlab.yaml` here are refused
naming them and `--lab`; `up --trust`/`--open` pre-answer the end of a
boot. CI, coding agents and scripts write the config first and name the lab.

The sections below are the groups `agentlab --help` prints, in the same order.

## Setup

| Command | What it does |
|---|---|
| `up` | Check docker's CPUs and memory against this configuration's floors, then create the kind cluster, deploy Dex and the enabled components, and verify the OIDC chain end to end. Idempotent: unchanged re-runs are no-ops. On a terminal it ends by asking what the summary used to only describe: whether to trust the lab CA while it is untrusted, then whether to open the portal. `--trust` and `--open` (or `--trust=false`/`--open=false`) pre-answer both for scripted runs; off a terminal nothing is asked. See [TLS](tls.md). |
| `configure` | Discover this machine, then ask for the lab configuration (or keep it with `--defaults`) and save `agentlab.yaml`. Without an `agentlab.yaml` yet, on a terminal, it first asks one question — the detected defaults, or customize — and only *Customize* runs the form; `up` (and every command that has to create the file on the way) asks the same. With an existing file the form opens with its values. Flags below. |
| `trust` | Install the lab CA into the system and browser trust stores (one sudo prompt; reversible). See [TLS](tls.md). |

## Everyday

| Command | What it does |
|---|---|
| `open <portal\|agents\|prometheus>` | Open a lab URL in the browser and print it (so it can be copied where the opener finds no browser — SSH, WSL): `portal` is Backstage, `agents` the kagent UI, `prometheus` the lab Prometheus's web UI on the edge (`https://observability.<domain>/prometheus`, the path Backstage queries). The target is required; without one, the refusal names them. Refused when the target is disabled in `agentlab.yaml`, when the cluster is not running, or when the target does not answer yet (a short reachability probe, before any trust question, so a sudo prompt is never spent on a command that then opens nothing) — a plain fact instead of an error page in the browser. While the lab CA is untrusted, `open portal` and `open prometheus` offer `agentlab trust` first on a terminal and warn off one; `open agents` is plain HTTP on loopback and asks nothing. |
| `list` (`ls`) | Every lab registered on this machine: its name, directory, cluster state (`running`, `exited`, `not created`), enabled components with the chart, the portal and muster URLs (with the port suffix when the edge is not on 443), and whether its lab CA is trusted here; `*` marks the current directory's. Docker and the files answer, so it works while a lab is down. `-o json` for scripts. It never asks which lab. |
| `status` | The lab's live state, for the lab here (or `--lab`): the chart the cluster runs — its version, whether it is a dev chart (a chart directory's build or a branch's dev build), its Helm revision and which agentlab installed it from where — against the chart `agentlab.yaml` installs; when the two differ, the drift with both versions and which side is behind (an `agentlab.yaml` put back from a copy without a platform run pins an older release than runs) and the two ways to end it — `agentlab platform` installs the configured chart over the one in place, `agentlab configure --adopt-chart` writes the chart in place into the config; and the platform HelmReleases, how many are Ready and every other one with helm-controller's message. An `overlay` line per `platform.valuesFiles` entry: the file and every value it sets (`components.kagent.versionRange=1.15.0-rc.4`; the first eight, then a count), an unreadable one named as such, one the release in place does not carry yet marked, and one the release in place was installed with that `agentlab.yaml` no longer lists (every platform run records its overlays in the revision's description, which the `chart` line shows) — so a lab handed on with a proof's pins never reads as the chart's own component ranges; `overlays` and `staleOverlays` in JSON. A `registry` line: the lab registry container (`<cluster>-registry`) running, stopped, or missing, which `agentlab platform` recreates (`registry` in JSON). `-o json` for scripts (`drift` carries the line). | `pods [-n <namespace>]` | The lab's pods across namespaces through the embedded client, shaped like `kubectl get pods -A` (NAMESPACE, NAME, READY, STATUS with a waiting reason such as `ImagePullBackOff`, RESTARTS, AGE); `-n` narrows to one namespace. Refused with `agentlab up` when the cluster is not running. |
| `logs <component>` | Tail a component's logs: `backstage`, `dex`, `klaus-gateway`, `mcp-prometheus`, `muster` or `prometheus`. |
| `login [email]` | Log in as a lab user: the headless password grant, or `--browser` for the real Dex login page (authorization-code flow, which asks for the user itself). Either way it prints the token claims and writes `.token` and `kubeconfig.oidc` for that user. `--password` overrides the one in `agentlab.yaml`. `--audience` (repeatable, default `kubernetes`, headless only) names the token's audience: `kubernetes` for the apiserver, `agent-platform` for muster and the agent-platform MCP servers behind it (workspace-manager, agent-manager, model-manager), `dex-k8s-authenticator` for muster's own Kubernetes writes. Any set besides `kubernetes` alone is minted by the `agent-platform` Dex client, so its token carries `agent-platform` too; `kubeconfig.oidc` is written only when the token carries `kubernetes`. |
| `turn (--list \| --template <name> <prompt> \| --session <id> --delete)` | One conversation with an agent as a lab user, the way the surfaces drive it: the user's Dex id_token on the kagent controller's gRPC route through the edge. `--list` prints the roster that user sees — `ListAgents` as that person (each Agent with the AgentTemplate and the Harness it pairs), or the gRPC status when the controller refuses. With `--template` and one prompt it creates a `Session` of the Agent that pairs the template with a Harness — the template's Agent that reports Ready, the one the portal picks; `--harness` picks the Agent pairing the template with that Harness — streams one turn, prints the answer and the terminal task state, and deletes the session. `--user` picks the lab user (default: the first admin). `--keep` leaves the session for a later `--session <id>` turn (`--instance` is the former name) and prints the command that deletes it: `--session <id> --delete` deletes a kept session as the `--user`, its creator, the way a turn's own cleanup does (`DeleteSession`, retried while its runtime work settles, releasing its actor and snapshot), reads it back gone, and refuses an id that user cannot see — another user's, or one already gone; and `--session … --suspend` suspends it to the snapshot store and resumes it before the turn, the proof that a conversation survives the snapshot. The terminal status message's metadata (a harness's usage of the turn) is printed when present. A turn that pauses for tool approval prints the request and stops; `--decide approve` or `--decide reject` (with `--reason`) answers every request until the task settles. `--events <file>` writes every streamed A2A event as one JSON object per line, the raw material of a parser fixture. `--session <id> --share-with <email>` has the `--user` share the session read-write with another lab user (`--share-ttl` bounds how long the share's token grants access; default until revoked), runs the turn as that user with the share token (their own Dex token plus the token, which adds to their identity), and revokes the share afterwards. |

`kubectl --kubeconfig kubeconfig.oidc` after `login` is the OIDC path — the
way to verify what a specific user can do. The kind admin context bypasses the
platform and OIDC entirely.

`login --audience agent-platform` is the headless way to call muster as a lab
user, the token a person's portal sign-in carries: send `.token` as the bearer
to `https://muster.<domain>/mcp`, and the agent-platform MCP servers answer
(`x_workspace-manager_list_workspaces` among them). Add `--audience kubernetes`
when the same call reaches mcp-kubernetes or kubectl.

## Keeping agentlab current

`agentlab self-update` installs the latest GitHub release for your OS and
architecture — the command muster and mcp-kubernetes have too — at
`~/.local/bin/agentlab` (`$XDG_BIN_HOME`). A release installed anywhere else
(`~/go/bin`, a download folder) moves there on the first `self-update`, also
when nothing is newer, and leaves a link at its old path, so either order of
the two folders on `PATH` runs the one binary; `self-update` says when
`~/.local/bin` is not on `PATH`. `agentlab self-update --check` only reports the running and the
latest version, with exit status 125 when a newer one exists (for scripts). A
binary without a release version (`agentlab --version` says `dev`) is
refused: reinstall it from a release or with `go install`. A `go build` from
a checkout carries Go's pseudo-version (`v0.19.3-0.20260908…-8536d36`) and
is treated as what it is: after the tag before it, before the tag after it.

**Every release binary is verified before it is installed.** CI (the
architect orb) signs each `agentlab-<os>-<arch>` with cosign — keyless, the
CircleCI pipeline's identity, recorded in the Rekor transparency log — and
publishes the signature next to it as `agentlab-<os>-<arch>.bundle`.
`self-update` downloads both and installs the binary only after the bundle
verifies against the Sigstore public-good trust root for a CircleCI build of
`github.com/giantswarm/agentlab` (the shared
[`selfupdate-cosign`](https://github.com/giantswarm/selfupdate-cosign)
validator, the one muster and the other Giant Swarm CLIs use). A release
without a bundle for your platform is refused before anything is downloaded; a
download that does not match its signature is refused before anything is
written. Either way the installed binary stays as it is, and the error says
why. The hint below installs nothing, so it does not need the bundle.

### Release candidates

Release candidates (`v0.97.0-rc.1`, published as GitHub prereleases) are left
out unless you ask for them: `agentlab self-update --pre` installs the newest
of the release candidates and the stable releases, in semver order
(`v0.96.0-rc.6` < `v0.96.0` < `v0.97.0-rc.1`), verified like any release. A
release candidate installed by hand thereby moves to the next one, or to the
stable release that follows it; `--check --pre` reports the same without
installing. Without `--pre` nothing changes: only stable releases count, and
an rc binary with nothing stable newer is pointed at `--pre`. The hint below
names stable releases only.

Every write of `agentlab.yaml` records the agentlab that wrote it in the
header (`# Written by agentlab v0.97.0-rc.1.`), a comment older releases read
past. A field this binary does not know is refused, naming that version and
the command that installs it: `agentlab self-update`, or
`agentlab self-update --pre` when the file was written by a release
candidate.

Every command also starts with a one-line hint on stderr while a newer
release is out — devctl's per-command check, with two deliberate differences:

- **A hint, never a gate.** An outdated agentlab runs every command the same;
  nothing waits for you to update.
- **It gives up fast.** The GitHub round trip is capped at two seconds, and
  its answer is cached for an hour under your user cache directory
  (`~/.cache/agentlab/latest-release.json` on Linux,
  `~/Library/Caches/agentlab/` on macOS). A failed attempt is remembered for
  ten minutes, so a machine without internet is not held up on every command,
  and the last known answer keeps being shown meanwhile.

`self-update` and the hint read the releases with a token when one is at
hand: `GH_TOKEN`, else `GITHUB_TOKEN`, else the token of gh's signed-in
account (`gh auth token`). Without one the call is anonymous, under GitHub's
limit of 60 calls an hour shared by every machine behind the same address;
`self-update` says which it used, and when that limit is spent its error says
the call was anonymous and which variable to set.

`AGENTLAB_NO_UPDATE_CHECK=1` silences the hint (`self-update` itself always
works); `dev` builds never check.
